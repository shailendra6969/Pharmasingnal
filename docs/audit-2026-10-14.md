## 3. Architecture & code-quality review

**Layering** matches the plan (routes → services → repositories): routes only parse/serialize ([`app/api/__init__.py`](../app/api/__init__.py)), services hold business logic, repositories own SQL. Statistics are isolated in `app/statistics/` with a single authoritative formulas module.

**SQL safety — clean.** All user values are parameterized (`%s`); `sort_by`/`order` are whitelisted dicts in [`signal_repository.py`](../app/repositories/signal_repository.py); dynamic identifiers use `psycopg2.sql.Identifier` ([loader.py](../app/repositories/loader.py)) or module constants; no `eval`/`exec`/`pickle`/`subprocess` anywhere; zero TODO/FIXME markers.

**Concurrency.** Ingestion is single-writer via `pg_try_advisory_lock` with orphaned-run recovery ([run_ingestion.py](scripts/run_ingestion.py)); refresh API is single-flight under an `RLock` with orphan recovery ([refresh_service.py](app/services/refresh_service.py)). Both have dedicated tests (concurrency refusal, crash-mid-run, orphan recovery).

**Statistics core** ([disproportionality.py](app/statistics/disproportionality.py), [engine.py](app/statistics/engine.py)): PRR/ROR/log-CI formulas are correct and hand-verified by 14 unit fixtures; Haldane–Anscombe zero-cell handling and Yates χ² are documented; the engine commits atomically (rollback on error), uses case-level `DISTINCT` counts, and enforces the full-background rule. **One methodology question** (see §5): screening uses the *Yates-corrected* χ² ≥ 4, whereas the classic Evans & Sturgley screen uses uncorrected Pearson χ² — conservative, but unverifiable against the spec because **the spec file is not in the repository**.

**Ingestion loader** ([loader.py](../app/repositories/loader.py)): COPY text-format escaping is correct (backslash escaping precedes the NULL marker, so a literal `\N` value cannot become NULL); staging tables are dropped on both success and failure; `apply_dedup` documents and relies on record-set completeness, which `run_ingestion._dedup_pass` guarantees. Re-ingest is idempotent (`ON CONFLICT DO NOTHING`) — with the tradeoff noted in §6 (existing rows are never updated).

## 4. Findings

### 4.1 H1 (High) — Drug-profile demographics double-count cases

`get_drug_profile` in [signal_repository.py](app/repositories/signal_repository.py) computes the **sex** and **age** distributions with `COUNT(*)` over `case_drugs ⋈ cases`, while `total_cases`, **roles**, and **quarterly trend** use `COUNT(DISTINCT primaryid)`. A case may list the same drug under several `drug_seq` rows, so the demographic distributions count drug rows, not cases.

Measured on the live DB for the page the audit opened (`/drugs/DUPIXENT`):

| Quantity | Value |
|---|---|
| Distinct cases (what the page header shows) | **212,423** |
| `case_drugs` rows summed over the sex distribution | **286,959** (+35.1%) |

The page therefore displays demographic distributions that sum to a third more than its own stated case total. The event profile is **not** affected (`case_events` is unique on `(primaryid, event_term)`, so row count = case count there).

- **Why no test caught it:** no test exercises `/drugs/<drug>` or the drug-profile service at all.
- **Fix:** use `COUNT(DISTINCT c.primaryid)` in the sex and age queries (two lines in `get_drug_profile`), and add an integration test asserting `sum(sex_distribution.cases) == total_cases` on a fixture with a duplicated `drug_seq`.

### 4.2 H2 (High) — `/api/data-quality` serves stale counts as `database_counts`

[SystemService.data_quality](../app/services/system_service.py) returns `report.get("database_counts")` — counts **snapshotted into the stored report at ingest time** (2026-10-10 20:17), not live queries. Measured divergence today:

| Field | Stored report says | Live DB says |
|---|---|---|
| `cases_current` | 3,201,449 | **2,831,775** |
| `signal_scores` | 607,531 (the q1-only era) | **2,139,259** (8-quarter recompute of 10-11) |

Worse, the stored snapshot's `cases_current` (3,201,449) also contradicts the README's measured post-run state for the same timestamp (2,831,775), i.e. it was captured mid-run before that run's dedup pass finished. Consumers cannot distinguish "measured at ingest" from "current DB state", and the field name implies the latter. `stage_totals`/`per_quarter` are legitimately ingest-time; `database_counts` is not.
- **Fix:** compute `database_counts` live (the loader already exposes `database_counts(conn)`) or rename to `database_counts_at_ingest` and add a separate live block. Add a test that recomputes signals between two API calls and asserts the counts move.

### 4.3 M1 (Medium) — `/drugs/<drug>` takes 13.3 s

Profile pages run **six sequential aggregate queries**, each re-scanning the drug's ~287k rows. Measured per-query (DUPIXENT, warm connection):

| Query | Time |
|---|---|
| roles (`COUNT(DISTINCT)` GROUP BY) | **4.36 s** |
| sex | 1.60 s |
| total_cases | 1.31 s |
| age | 1.05 s |
| quarterly trend | 1.03 s |
| top signals (indexed) | 0.01 s |
| **sum** | **≈9.4 s** (+ cold-cache/template → 13.3 s observed) |

`/events/<event>` = 4.1 s; dashboard is fast. Options: collapse roles+sex+age+quarterly into one pass (`GROUPING SETS` / CTE over the drug's rows), cache the profile per drug, or materialize per-drug aggregates at refresh time. Existing indexes (`idx_case_drugs_drug_current`) already serve the lookups; the cost is repeated aggregation, not scanning.

### 4.4 M2 (Medium) — Security hardening gaps

- **No security headers**: responses carry none (no CSP, `X-Content-Type-Options`, `X-Frame-Options`) and leak `Server: Werkzeug/3.1.9 Python/3.12.9`. Spec §48 compliance exists for error bodies (no stack traces — verified live on 404/500) but not headers.
- **No rate limiting** on public endpoints; `ILIKE '%q%'` search endpoints and profile pages are cheap to hammer (leading-wildcard scans on 607k-row `signal_scores`).
- The running instance is the **Werkzeug dev server**; acceptable for local use, not for deployment (Phase 9).
- Positive: admin auth is fail-closed (`503` unconfigured, `401` wrong key, `hmac.compare_digest`), malformed input is sanitized (measured), `.env` and licensed/reference data are gitignored, and no credentials appear in the repo.

### 4.6 M4 (Medium) — Documentation & plan drift

1. **The spec is missing.** "spec §…" is referenced throughout code and docs (100+ citations), but no spec file exists in the repo — conformance claims cannot be independently checked.
2. **README status line is stale**: still says "Phases 1–2 implemented" although Phase 3 (Flask API/UI, admin refresh, the seven-stage orchestrator) is implemented, documented and tested.
3. **Migration numbering**: `003_analytics_indexes.sql` and `003_refresh_jobs.sql` share the `003_` prefix. `migrate.py` keys by filename in lexical order so both apply correctly today (verified), but the sequence no longer numbers cleanly.
4. **Schema comment drift**: `001_initial_schema.sql` says pgvector "lives in 002_pgvector.sql", but `002_signal_analysis.sql` is what exists.
5. **Plan file list**: `app/statistics/contingency.py` (Phase 2 deliverable) was folded into `disproportionality.py` — coverage intact, file absent.
6. `data/processed/quarterly_refresh_latest.json` (linked from README) does not exist yet — correct, since no refresh run has happened (`refresh_jobs` table: 0 rows); flagging only so it isn't mistaken for a broken link.

### 4.7 Low-severity observations

- `settings.admin_api_key()` / `database_url()` are `@lru_cache`d → key rotation requires an API restart (undocumented).
- `refresh_repository.finish_job` validates `status` with `assert` (stripped under `python -O`).
- Dead no-op block in `disproportionality.compute` (`if t.a < min_cases … pass`).
- Re-ingest never **updates** an already-loaded `primaryid` (`ON CONFLICT DO NOTHING`) — corrections to a previously loaded report require manual deletion. By design for idempotency, but undocumented.
- User `%` is honored and `_` is not escaped in LIKE filters (stated wildcard semantics; perf angle in M2).
- `outcomes` table exists but OUTC is never parsed (schema says "later pipeline extension") — dead until then.
- Empty scaffolds awaiting Phases 4–9: `app/{rag,agents,verification,evaluation,monitoring,models,schemas,utils}`, `tests/e2e/`, `docker/`, `frontend/`, `notebooks/` — consistent with the plan; Docker remains unverifiable (not installed).

## 5. Strengths worth preserving

1. **Suite is fully green**: 155/155, exit 0, including e2e seven-stage refresh, hand-calculated statistics, and incident-driven hardening tests.
2. **Data integrity verified live**: one current version per case (2,831,775 = distinct case_ids, 0 duplicates); engine `background_n` uniformly matches the live current count; stale rows are retained, never deleted.
3. **Parameterized SQL everywhere** with whitelisted sort/filter identifiers — no injection surface found.
4. **Fail-closed admin auth** with constant-time compare; no secrets or licensed data in git.
5. **Atomic, deterministic engine writes** with rollback; staging tables self-cleaned.
6. **Single-writer locks + orphan recovery** in both ingestion and refresh, each with regression tests (including an RLock self-deadlock bug found by faulthandler and fixed).
7. **README is evidence-dense**: measured tables with dates, incident narratives, and every linked artifact verified present on disk.
8. **Input robustness**: malformed query params degrade to defaults (measured live), never 500s.
9. **Reference/licensing handled correctly**: SIDER CC BY-SA attribution documented, files gitignored with re-download instructions printed by the tool.
10. **Honest reporting discipline** (plan §73): Docker/LLM phases marked unverified rather than passed.

**Open methodology questions for the spec owner:** (a) Yates-corrected vs uncorrected χ² ≥ 4 screening threshold; (b) continuity-corrected PRR values may pass the PRR ≥ 2 screen (flagged `continuity_corrected`, but the screen still counts them); (c) primary-suspect mode pairs mode-filtered row totals against the full-background N — confirm intended.
